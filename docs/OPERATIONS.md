# 知乐：从分享给朋友开始

## 这一版已经做到

- 首次进入即有场景入口；公开推荐随后加载，不用先搜索才能看到内容。
- 首页、搜索、我的音乐三个底部入口，切页保留播放器。
- 大封面播放详情、可收起歌词、独立的更多操作。
- 最近播放留在本机，方便回来继续听；空记录有明确的第一步。
- 首页分享链接、反馈入口与更新日志；GitHub 提供问题和功能建议表单。
- 下载页加入可暂停的轻量动效，尊重系统“减少动态效果”。

没有启用访客追踪，没有虚构热门数据，首页的公开推荐也不是个人 AI 推荐。

## 建议的首月节奏

1. 先邀请 20–50 位朋友试用。这是招募目标，并非已有用户数。优先覆盖不同 Android 型号，收集安装、首播、换源三个环节的问题。
2. 每周先修最常见的阻碍，再更新一个有明确主题的场景入口。当前入口在 `internal/web/templates/partials/home.html` 配置，搜索真实平台歌单；它们不是人工审核过的精选歌单。
3. 维护公开更新日志：新增了什么、修了什么、还存在哪些已知限制。更新保留应用 ID 与签名，方便覆盖安装。
4. 在下载页、朋友分享与仓库使用相同名称和下载地址；部署后可把首页分享函数的链接换成自己的公开 HTTPS 下载页。

初期通过自愿反馈关注：能否安装、第一次是否找到并播放歌曲、是否收藏、下周是否还用。以后如要量化，可在明确告知和可退出的前提下统计最少的匿名事件。不要收集搜索词、歌曲历史、Cookie 或账号资料来替代产品判断。目前并未接入此类统计。

## AI 应该先做什么

以下是产品建议，当前版本尚未接入 AI，也不会产生 AI 调用费用。

**第一优先：一句话找歌。** 例如“给我适合晚上写代码、不太吵的歌”。模型只把意图转换成搜索条件，再调用现有搜索，展示实际查到的歌曲；用户确认后才创建歌单。无结果就换条件，不让模型编造歌曲 ID、下载链接或可播放承诺。

**第二优先：整理歌单。** 为用户选中的歌曲拟标题、分组和去重。先用本地规则处理精确重复，再让模型辅助语义分类。只发送用户主动选中的必要元数据。

**之后再评估：个人推荐。** 等用户确实有持续使用和主动授权，再评估听歌偏好；为推荐提供“少推荐此类”和解释入口。先比较首播成功、收藏反馈和响应时间，再决定是否扩大。

技术上可使用工具调用连接真实搜索，结构化输出约束搜索字段。这是基于现有能力作出的方案判断，不能保证模型建议一定符合口味。参考：[OpenAI 工具调用](https://developers.openai.com/api/docs/guides/function-calling)、[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)。

未来若提供公共 AI 服务：密钥只放服务器，应用通过有身份校验和限额的接口请求，增加超时、重试上限、费用额度和关闭开关。不要把服务端密钥打进 APK。先试一句话找歌，暂不增加一个独立聊天页。
